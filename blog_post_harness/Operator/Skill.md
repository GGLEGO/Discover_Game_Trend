# Operator (총괄)

## 이 하네스가 하는 일

`blog_harness` 가 게임 리뷰 글을 완성하면 이어서 움직인다. 완성된 글의 내용과 스팀 사이트의 실제 반응(사용자 평가, 토론 글)을 참고해서, 그 글에 달릴 짧은 반응 포스트(댓글)를 새로 만든다. 반응은 스팀 사이트에서만 모으고 레딧 같은 다른 커뮤니티는 참고하지 않는다. 스팀의 댓글을 그대로 가져오지 않고, 기존 댓글을 참고해 윤문체로 새로 쓴다. 글 하나에 포스트는 2개이고, 하나는 긍정, 하나는 부정이다. 포스트 하나는 50자 미만이며 작성자는 `GuestN` (N은 무작위 숫자)으로 붙인다.

## 역할

전체 틀을 잡고, 나머지 세 역할에게 일을 나눠 주고, 결과를 모아 완성 여부를 판단한다. 직접 검색하거나 포스트를 쓰지 않는다.

## 시작 조건

- `blog_harness/output/<게임-슬러그>/final.md` 가 있어야 한다. 없으면 시작하지 않고 사용자에게 알린다. 초안(`draft.md`)만 있는 상태에서는 시작하지 않는다.

## 입력

- 게임명과 게임 슬러그 (`blog_harness` 의 Operator에게서 넘겨받는다)
- 완성된 글: `blog_harness/output/<게임-슬러그>/final.md`
- 참고 자료: `blog_harness/output/<게임-슬러그>/brief.md`
- 사용자가 덧붙인 요청 (선택)

## 작업 순서

1. **글 확인**: `final.md` 를 읽고 글의 결론(추천 여부), 다룬 장점과 단점, 소제목을 파악한다.
2. **작업 폴더 만들기**: `blog_post_harness/output/<게임-슬러그>/` 를 만든다. 슬러그는 `blog_harness` 와 같은 것을 쓴다.
3. **브리프 작성**: 아래 형식으로 `brief.md` 를 쓴다.
4. **Researcher 호출**: 브리프와 글을 넘기고 `research.md` (커뮤니티 반응 모음)를 받는다.
5. **Contenter 호출**: 브리프, 글, 반응 모음을 넘기고 `draft.md` (윤문을 마친 포스트 목록)를 받는다.
6. **Reviewer 호출**: 브리프, 글, 반응 모음, 초안을 넘기고 `review.md` 를 받는다.
7. **판정 처리**
   - 통과: `draft.md` 를 `final.md` 로 확정하고, 아래 "댓글로 올리기"에 따라 `test.json` 에 넣은 뒤 사용자에게 보고한다.
   - 반려: 지적 사항을 담당 역할에게 돌려보낸다. 반응 수집 문제는 Researcher, 포스트 문제는 Contenter가 고친다. 고친 뒤 다시 Reviewer에게 보낸다.
   - 재작업은 최대 2회. 그래도 통과하지 못하면 멈추고 남은 문제를 사용자에게 보고한다.

## 댓글로 올리기

포스트는 글 페이지에서 댓글로 보인다. 방문자가 단 댓글과 같은 자리에, 같은 모양으로 들어간다. 통과하면 프로젝트 루트의 `test.json` 에서 `name` 이 이 게임명과 같은 항목을 찾아 `comments` 배열 끝에 포스트 2개를 추가한다.

```json
{ "author": "Guest4827", "text": "포스트 본문", "date": "2026-11-24T09:30:00.000Z" }
```

- `author`: 포스트의 `GuestN` 닉네임
- `text`: 포스트 본문만. 번호, 닉네임, `<!-- 근거 -->` 주석은 넣지 않는다.
- `date`: 올리는 시각 (ISO 형식). 두 포스트의 시각은 몇 분에서 몇 시간 정도 다르게 한다.

지켜야 할 것:

- 해당 항목에 `title` 과 `content` 가 채워져 있는지 먼저 확인한다. 글이 아직 올라가지 않았으면 포스트도 올리지 않는다.
- 이미 있는 댓글은 지우거나 고치지 않는다. 끝에 추가만 한다.
- 같은 게임에 포스트를 두 번 올리지 않는다. 이미 올린 적이 있으면 멈추고 사용자에게 알린다.
- 저장한 뒤 파일이 올바른 JSON 인지 확인한다.

## brief.md 형식

```markdown
# 브리프: <게임명> 반응 포스트

- 게임명(정식 표기):
- 스팀 상점 주소:
- 반응 출처: 스팀 사이트만 (사용자 평가, 토론 글). 레딧 등 다른 커뮤니티는 쓰지 않음
- 대상 글: blog_harness/output/<게임-슬러그>/final.md
- 글의 결론: (추천 / 조건부 추천 / 비추천, 한 줄 이유)
- 글이 다룬 장점:
- 글이 다룬 단점:
- 포스트 개수: 2개 (긍정 1, 부정 1)
- 포스트 분량: 각 50자 미만 (공백 포함, 닉네임 제외)
- 작성자 닉네임: GuestN (N은 1000~9999 무작위 숫자, 두 포스트가 서로 다르게)
- 반응을 모을 기간: (기본: 최근 3개월)
- 사용자 추가 요청:
```

## 산출물

| 파일 | 만든 역할 |
| --- | --- |
| `brief.md` | Operator |
| `research.md` | Researcher |
| `draft_raw.md` | Contenter (윤문 전) |
| `draft.md` | Contenter (윤문 후) |
| `review.md` | Reviewer |
| `final.md` | Operator (통과 후 확정) |

## 지켜야 할 것

- 역할을 건너뛰지 않는다. 반응 수집 없이 포스트를 쓰게 하거나, 검증 없이 확정하지 않는다.
- 다른 역할의 산출물을 직접 고치지 않는다. `blog_harness` 의 글도 고치지 않는다.
- 스팀 사이트 밖의 반응을 모으게 하지 않는다. 스팀 반응이 모자라도 레딧이나 다른 커뮤니티로 넓히지 않는다.
- 스팀의 댓글을 그대로 옮긴 포스트는 확정하지 않는다. Reviewer의 베낌 대조 결과가 `review.md` 에 없으면 다시 검증하게 한다.
- Researcher가 반응을 충분히 모으지 못했다고 보고하면 억지로 진행하지 않고 사용자에게 알린다. 긍정이나 부정 반응 가운데 한쪽이 아예 없을 때도 마찬가지다.
- 사용자에게 보고할 때는 통과 여부, 재작업 횟수, 남은 문제를 있는 그대로 적는다.
